# Skill Eval Suite

This folder evaluates the three prompt-based "skills" that make up the AI
analysis pipeline (`templates/skills/metrics_analysis.md`,
`templates/skills/comment_analysis.md`, `templates/skills/synthesis.md`),
each **independently**, using real `claude` CLI calls (the same mechanism
`python/ai_analysis.py` uses in production).

Each skill can be run and inspected on its own, or chained so that Stage 2
consumes Stage 1's real output and Stage 3 consumes both. This lets you
tune one skill doc (e.g. `comment_analysis.md`) without having to
re-validate the others by hand every time.

## Current status

**Implemented now:** a config-driven runner per stage
(`metric_skill_eval.py`, `comment_skill_eval.py`, `synthesis_skill_eval.py`)
that takes a Qualtrics-style CSV (same format as
`example-data/topgolf_qualtrics_30_responses - DALLAS.csv`), runs it through
the real `generate_reports.py` ingestion, and calls the real skill via the
real `claude` CLI. Each run produces a human-readable Markdown report plus
the raw JSON, and a small set of mechanically-checkable assertions derived
from each skill doc's "Rules" section.

**Deliberately deferred:** synthetic edge-case CSVs (null resolution, zero
comments, severe-outcome comments, all-moderate metrics, etc. - see
"Planned test coverage" below). The skill docs' input/output schemas are
still moving, so hand-built edge-case fixtures would need to be
regenerated every time a schema changes. Once the schemas stabilize,
add CSVs under `test-data/` and wire them into `eval_config.json` as
additional named sources - the runners are already written to support
more than one source per stage, not just the Dallas baseline.

## Layout

```
python/evals/
  EVALS.md                 # this file
  eval_config.json          # default CSV/venue + output locations + chain wiring
  eval_common.py            # shared helpers: CSV -> venue_data, payload building,
                             # claude CLI invocation, schema validation, Markdown report writer
  metric_skill_eval.py       # Stage 1 runner (metrics_analysis.md)
  comment_skill_eval.py      # Stage 2 runner (comment_analysis.md)
  synthesis_skill_eval.py    # Stage 3 runner (synthesis.md)
  test-data/                 # (future) edge-case CSVs, once schemas are stable
  output/
    <run-id>/
      venue_data.json          # generated by generate_reports.py for this run
      metrics_analysis.json    # Stage 1 raw output
      metrics_analysis.md      # Stage 1 human-readable report
      comment_analysis.json    # Stage 2 raw output
      comment_analysis.md      # Stage 2 human-readable report
      synthesis.json           # Stage 3 raw output
      synthesis.md              # Stage 3 human-readable report
```

`eval_common.py` reuses `ai_analysis.py`'s existing payload builders
(`_build_metrics_payload`, `_build_comment_payload`), skill text constants
(`METRICS_ANALYSIS_SKILL`, etc.), the `claude` CLI invocation
(`_invoke_claude`/`_extract_json`), and its schema validators
(`_validate_metrics_analysis`, etc.) rather than re-implementing them, so
the eval suite never silently drifts from what production actually sends.

## Running a stage

All commands are run from `python/evals/`.

```bash
# Stage 1: metrics_analysis.md, using the default CSV/venue from eval_config.json
python metric_skill_eval.py

# Same, but with an explicit CSV / venue / run id
python metric_skill_eval.py --csv "../../example-data/topgolf_qualtrics_30_responses - DALLAS.csv" --venue-key dallas --run-id dallas

# Stage 2: comment_analysis.md - by default chains from output/<run-id>/metrics_analysis.json
python comment_skill_eval.py --run-id dallas

# Stage 2, but against a hand-picked Stage 1 result instead of the chained one
python comment_skill_eval.py --run-id dallas --metrics-input path/to/other_metrics_analysis.json

# Stage 3: synthesis.md - by default chains from output/<run-id>/{metrics_analysis,comment_analysis}.json
python synthesis_skill_eval.py --run-id dallas
```

Each run prints a pass/fail summary of the automated checks to the console
and writes `output/<run-id>/<stage>.md` - open that file to actually judge
quality: does the characterization make sense, are the themes specific and
not invented, does the synthesis narrative track the inputs, etc. The
automated checks catch only what's mechanically checkable (ordering,
schema, banned phrases, count bounds) - they are not a substitute for
reading the output.


## Planned test coverage (once schemas are stable)

The intent is for each stage to have several small, targeted test cases -
not just one end-to-end run against the Dallas data - each aimed at a
specific rule from that skill's doc:

**Stage 1 (`metrics_analysis.md`)**
- All metrics land in "Moderate" -> all five should still be flagged.
- `resolution_avg` is `null` (no issues reported) -> must never produce a
  `resolution` flag.
- A high `issues_pct` -> magnitude should track the raw percentage closely.
- `characterization` must never contain network/comparison language.

**Stage 2 (`comment_analysis.md`)**
- Zero comments -> `themes` must be `[]`.
- Comments present but all generic ("great time!") -> `themes` must be
  `[]` (no invented themes from sentiment alone).
- A single comment describing a severe outcome (left without playing,
  unresolved safety issue) -> resulting magnitude must be >= 40-50 even
  with a low mention count.
- A comment with both a positive and a negative theme -> must be split
  into two separate theme entries with opposite polarity.

**Stage 3 (`synthesis.md`)**
- `impact` must reflect the true top-3 of the combined
  metric-flags + themes pool, sorted by magnitude - not a topic-based or
  stage-based ordering.
- `recommendations.critical` must address the #1-ranked negative entry
  from the combined pool; `maintain` must reinforce the #1-ranked
  positive entry.
- `ups`/`downs` must each have 2-3 items and may include lower-magnitude
  entries not present in `impact`.
- `overview`/`ups`/`downs`/`impact`/`recommendations` must never state or
  imply a network average or cross-venue comparison.

To add one of these once ready: add a CSV under `test-data/` reproducing
the scenario, register it as a named source in `eval_config.json`, and add
a test id under the relevant stage referencing that source id plus which
mechanical checks apply. Because each check in `metric_skill_eval.py` /
`comment_skill_eval.py` / `synthesis_skill_eval.py` is a small standalone
function, adding a new scenario-specific check is additive - it doesn't
change how existing checks or the Markdown report are produced.

## Notes

- Cache: unlike `ai_analysis.py`'s production pipeline, these runners
  always make a **fresh** `claude` CLI call (no cache) so that editing a
  skill doc is always reflected immediately in the next eval run.
- Nothing in this folder is imported by production code
  (`generate_reports.py`, `ai_analysis.py`, `create_*_reports.py`); it's a
  standalone tool for iterating on the skill docs.
